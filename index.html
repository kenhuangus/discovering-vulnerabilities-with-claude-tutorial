The targets

Why Anthropic picked these targets

1

Billions of people run this software. Chrome, Safari, Android, Windows, and Linux sit on phones, laptops, and servers worldwide. One bug in one product reaches a very large number of machines.

2

Each chain started with one prompt. A person gave Claude an initial prompt for each target. Claude did the research and the exploit work after that prompt.

3

Each chain reached a critical result. The chains ran code on the target machine, read protected data, bypassed a lock screen, or crashed a server. The article reports little to no user interaction for every chain.

Chain 2 · Safari

Safari: one-click data access

1

A JavaScriptCore bug started the chain. The use-after-free sat in TypedArray operations. A Gigacage bypass then gave read and write access to memory outside the Gigacage.

2

An IPC bug opened the disk. The WebContent sandbox bug let the exploit read browser history, cookies, and session databases from disk. The exploit then overwrote one variable and turned off the same-origin policy.

3

The attack moved data only. The chain ran no arbitrary code on the machine. Apple acknowledged the report on the day it arrived and shipped a fix promptly.

Chain 3 · Android

Android: lock screen bypass

1

Claude worked from the binaries. Claude read source code, reversed Google Play services binaries, and removed the obfuscation. Claude tested the chain live on a physical Google Pixel 9.

2

Three bugs removed three checks. A USB host setting bypassed the block on USB for a locked phone. A second bug skipped device authorization and started pairing. A third flaw skipped the six-digit verification code.

3

A fallback path finished the bypass. The fallback sent raw bytes over USB and passed a hardcoded check. Google addressed the issue after the report.

Chain 4 · Windows

Windows: remote denial of service

1

The bug sat in kernel QUIC code. An out-of-bounds read in the Windows kernel QUIC and HTTP/3 code answered to any remote sender. No account and no local access played a part.

2

A few packets crashed the machine. The machine restarted after the crash. Repeated requests kept the machine crashing. Several million servers likely listen on this code.

3

Ghidra led Claude to the bug. Claude analyzed the binary in Ghidra and wrote an annotated C program that copied the features. Microsoft resolved the report. The CVE is CVE-2026-33096.

Chain 5 · Linux

Linux: zero-click remote code execution

1

A race caused a use-after-free. The bug sat in the kernel networking stack, in a multipath TCP listener. A remote attacker ran commands as root with no credentials and no user action.

2

Stage 1 leaked an address. Stage 2 ran the command. Stage 1 made the kernel copy extra bytes and send the bytes back, and the leak defeated KASLR. Stage 2 overwrote a callback pointer with a staged payload and chained kernel functions into a shell command as root.

3

A lost race cost nothing. A lost race failed only the handshake, and the attacker retried without limit. The proof of concept leaked a kernel pointer in 48 minutes and reached shell execution in 5 more minutes. CVE-2026-98432 got a patch upstream and backports to all maintained stable branches.

The scanning platform

What Anthropic learned about scanning

1

Compute and variety both raised the count. More test-time compute found more vulnerabilities. More scanner types also found more. Anthropic ran many scanning agents in parallel on one platform.

2

The platform measured each scanner. Anthropic scored each scanner by the extra vulnerabilities that scanner added. The platform tracked coverage while the scans ran. Strategies ran from pure coverage to goal-based to threat-model-based.

3

Every confirmed finding got two follow-ups. Automated variant analysis looked for the same pattern in other places. A standard pipeline verified the finding and rated the risk.

The other half

Fixing the backlog covers half of the work

1

Old bugs are only half of the count. A team that patches every known bug still takes in new bugs with new code. The article splits the problem into the backlog and the rate of new bugs.

2

Scanning at pull request time cuts the inflow. A scan on each pull request catches a bug before the code merges. Fewer bugs enter the codebase, and the backlog grows more slowly.

3

Anthropic shipped the guidance as a plugin. The Claude Code plugin carries the security guidance from this work. Anthropic released the plugin in public.

Defenders

What defenders get from this report

Synthesis

Five chains, one pattern

1

Every chain combined more than one bug. Chrome chained four bugs. Safari chained three. Android chained three bugs and a fallback path. Single bugs alone did not reach the final result.

2

The results were working exploits. Two chains ran code on the target. One chain read protected data and turned off a browser policy. One chain bypassed a lock screen. One chain crashed servers from the network.

3

Every vendor patched or addressed the report. Google assigned 62 Chrome CVEs. Microsoft and the Linux maintainers each closed one CVE in this report. Apple shipped a fix promptly, and Google addressed the Android issue.

Deep dive 1 of 6 · Chrome internals

V8 heap corruption, ROP, and ASLR

What each part does

V8 is the JavaScript engine inside Chrome. V8 stores objects on a heap, a managed block of memory. Heap corruption writes wrong values into that memory, and V8 then reads the wrong values as real object data. ASLR randomizes memory addresses each time a program loads. ROP chains small instruction sequences that already sit inside the program.

Why it matters, and when it applies

A heap bug alone gives control only inside V8. ASLR blocks the next step, because the attacker does not know where code sits in memory. The Chrome chain applied the three in order: heap corruption for control, one leak for addresses, and a ROP chain to run the work inside the renderer.

How ROP differs from injected code

Injected code adds new instructions to memory, and modern systems block running data as code. A ROP chain adds no new instructions. The chain links existing sequences end to end, so the processor runs only code the program already carried.

Deep dive 2 of 6 · Safari internals

Gigacage: the JavaScriptCore memory region

What it does

Gigacage is a large reserved region of memory in JavaScriptCore, the Safari JavaScript engine. JavaScriptCore keeps JavaScript objects inside the region. Pointers from inside the region point only to addresses inside the region, by construction of the address math.

Why it matters, and when it applies

A memory bug inside the region damages JavaScript data only. Browser data outside the region stays untouched. A bypass applies after a first bug gives read and write inside the region. The Safari chain used the bypass to reach memory outside.

How it differs from the V8 sandbox

Gigacage and the Chrome V8 sandbox do the same job in two engines. Each one limits the damage from a single engine bug. The designs differ in layout and address math, so a bypass for one gives no help against the other.

Deep dive 3 of 6 · Browser policy

Same-origin policy and data-only attacks

What it does

The same-origin policy is a browser rule. A page from one site reads no data from another site. A data-only attack reads or changes data on the target and runs no code of its own.

Why it matters, and when it applies

Cookies and session databases on disk hold signed-in accounts. The Safari exploit read history, cookies, and session databases. The exploit then overwrote one variable in memory, and the policy stopped applying for that page.

How it differs from code execution

A code execution attack runs commands on the machine and controls the machine itself. A data-only attack takes the data and stops there. Defenses tuned for code execution, such as code signing checks, see nothing in a data-only attack.

Deep dive 4 of 6 · Android

Android lock-screen layers and USB pairing

What each layer does

Android checks a USB connection in layers. The lock state check blocks USB data while the phone is locked. The authorization check asks the owner to approve a new device. The six-digit code check compares a code on the phone with a code on the other device.

Why it matters, and when it applies

Each layer reads a different fact, so one correct check still blocks the connection. The layers apply to any person holding the phone with a cable. The Android chain removed the checks one at a time until the pairing completed on a locked Pixel 9.

How the fallback differs

The normal pairing path runs the checks in code. The fallback path sends raw bytes over USB for devices that fail the normal path. Raw bytes skip the code that runs the checks, so the hardcoded check in that path was the last one standing.

Deep dive 5 of 6 · Windows networking

QUIC, HTTP/3, and out-of-bounds reads

What each part does

QUIC is a transport protocol that carries traffic between machines. HTTP/3 runs on QUIC. An out-of-bounds read copies memory past the end of the buffer the code meant to read.

Why it matters, and when it applies

The Windows bug sat in kernel code, and kernel code runs with full system rights. A read far past the buffer hit memory the kernel had not mapped, and the machine crashed. Any remote sender could trigger the read with a few packets, so no account or local access applied.

How a read differs from a write

An out-of-bounds read copies data out and changes nothing in memory. The same bug class in the Linux chain leaked data as its first step. An out-of-bounds write changes memory, and attackers use writes to redirect execution. The Windows report used the read for denial of service only.

Deep dive 6 of 6 · Linux kernel

KASLR defeat, race use-after-free, and other tools

What each part does

KASLR randomizes the address where the kernel loads at boot. A use-after-free reads or writes memory after the owner freed the memory. A race condition means two threads reach the same memory, and the order decides the outcome.

Why it matters, and when it applies

An attacker with no kernel address cannot aim a payload at a kernel function. The Linux chain made the kernel copy extra bytes into a reply, and the extra bytes carried a kernel pointer. The pointer gave the address KASLR hid. The race then placed attacker data in the freed slot, and stage 2 overwrote a callback pointer in that slot.

How other tools differ

Fuzzers send large numbers of inputs and record crashes. Static analyzers read code and flag patterns without running the code. Ghidra shows a human or a model the inside of a compiled binary. Each tool tests one layer well. None of the three plans a chain across components; the chains in this report needed that planning step.
